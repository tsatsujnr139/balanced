## Findings considered and rejected

- Running rules client-side after transaction creation: rejected because it
  creates a second write, can race, and can leave a partially categorized
  transaction.
- Making transaction category nullable: rejected because existing lists,
  filters, edit prefill, budgets, and stats all treat it as a string. A reserved
  `Uncategorized` snapshot preserves those invariants.
- Applying only one matching rule: rejected because overlapping tag rules are
  useful; V1 deterministically takes the first category and unions tags.
- Applying rules to edits, transfers, charges, or historical transactions:
  rejected for V1 because the user asked for new unclassified transactions and
  those paths have distinct financial semantics.
